## Current release and scientific dependency

Release run [39810108196](https://github.com/somehowchris/tika-indra-ocr-client/actions/runs/39810108196) on source `92ba8d5` (tag `v0.0.0-validation-20261022-92ba8d5`) passed every production gate and signing step for the consolidated producer: six images built, signed and verified, native and gateway process gates, Compose and Kubernetes accepted-work shutdown, the reference and trace gates, and the fresh-runner SDK/Chef proof. The amended 24-cell main/laboratory matrix then ran on those signed candidates. The run concluded failure only because its own report render rejected the evidence, through a defect in the report's admission code that `ffe12d7` corrected; run [39837656304](https://github.com/somehowchris/tika-indra-ocr-client/actions/runs/39837656304) rendered the report from the sealed index without re-measuring. The [results ledger](results.md) holds the measured numbers and keeps every earlier failed release attempt with its cause. No build speedup is claimed; a faster build is not established by moving cost into an uncounted producer or by reading a cache manifest.

Still open: the paired telemetry overhead timings, the independent numerical replay of the sealed evidence, a visual review of the complete rendered HTML, and a measurement of the shipped OCR/Tika CPU partitions and thread policy on the 1.1 engine, which the study did not measure. The release acceptance and the study cover source `92ba8d5`; any source whose production code differs from it needs a fresh signed release before those results apply to it. Continuous and telemetry synthetic studies remain distinct experiments, with their own exact drivers, resource admission and timing scopes.

## Review requirements retained

Actual shared-owner calls must preserve complete canonical reference groups and padding. Numerical comparisons bind owner/line/step identity, finite tolerances and discrete output decisions; compiler settings and request success alone cannot prove equivalence. Allocation counters cover their declared bounded operations, not total ONNX/HTTP allocations. Draining removes readiness and closes admission while accepted native work and response buffers retain ownership.

No evidence currently establishes a universally highest-accuracy setting, a generally superior two-CPU policy or an exhausted optimization space. Negative results and failed attempts stay in the record.
